# アーキテクチャと制約

[README](../README.md) に戻る。

Durably Factory の設計の核は、**工程の遷移（Durably ステップ）とエージェントの会話（セッション）を切り離すこと**、そして**エージェントが変更する作業ツリーと合否判定の対象を分離して固定すること**にあります。

## Candidate の固定と検証の分離

ここでいう Candidate とは、実装または修正を終えた時点のコードをスナップショット（またはコミット）として固定した不変の版です。検証・レビュー・承認・出力のすべてが同一の版を参照していることをハッシュやコミット SHA で保証します。修正が入って Candidate が更新されると、古い検証結果やレビュー結果は無効化され、新しい Candidate に対してやり直されます。

| ターゲット種別 | Candidate の固定方法                                     | 検証（`verify`）の仕組み                                                                         |
| -------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 同梱サンプル   | ファイルを別ディレクトリにコピーし、バイトハッシュで検証 | 開始時に別場所へ退避した受け入れテストを `node --test` で実行                                    |
| Git リポジトリ | 専用の Git worktree で作業し、コミット SHA で固定        | 開始時に固定した `check` コマンドを argv 配列で直接実行。追加・変更テストも 2 つのレビューで確認 |

`check` コマンドはシェルを介さず子プロセス（専用プロセスグループ）として起動するため、タイムアウトやキャンセル時に孫プロセスが残留しません。設定オプションの詳細は [リポジトリの設定](configuration.md) を参照してください。

## ステージ管理とチェックポイント復旧

```text
decision:N (policy が次工程を決定)
  └─ stages[decision.stage](...)
       ├─ code:   エージェント呼び出し ─▶ Candidate を固定
       ├─ verify: 固定した check を Candidate に対して実行
       ├─ review: review-a + review-b (step.all で新規セッション並列実行)
       ├─ approve: prepareWait ─▶ step.waitFor(Candidate ID)
       └─ finish / stop: 成果物出力または終了
```

- `src/factory/job.ts` は状態を保存・遷移させるだけで、承認待ち（`step.waitFor`）を `step.run` の内側に閉じ込めません。各ステージが返したイベントを保存してから `reducer` で状態を更新するため、再開時に完了済みステージを再実行したり、新しい作業ツリーに対して古いチェックを走らせたりすることがありません。
- 以下の 4 つの ID は役割が異なります。

| ID             | 識別する単位                                             |
| -------------- | -------------------------------------------------------- |
| `sessionId`    | プロバイダー（Codex / Claude）側の会話スレッド           |
| `operationKey` | 実装・修正・レビューなど、工程内の 1 つの論理作業        |
| `invocationId` | プロバイダーまたは `check` に送った実際の 1 回の呼び出し |
| `attempt.id`   | Durably がそのステップを試行した 1 回                    |

LLM 呼び出しと `check` コマンドは、**実行前に「開始チェックポイント」、完了後に「完了チェックポイント」**を保存してからステップを完了します。再開時に開始記録のみが残っていた場合、ローカルで再現可能な `check` は自動で再実行しますが、LLM 呼び出しはプロバイダー側ですでに実行・課金されている恐れがあるため `uncertain-invocation` として停止し、人の確認を待ちます（復旧手順は [日々の運用・復旧](operations.md#スリープやワーカー停止からの復旧)）。

## サンドボックス・権限・制約

`setup` や `check` はローカルの子プロセスとして実行されるため、信頼できるリポジトリとコマンドに対して使用してください。Git worktree は主にリポジトリ本体の作業ディレクトリを汚さず分離するための仕組みです。

- **Codex**: 実装・修正ロールは `workspace-write`（デフォルトではネットワーク無効、`sandbox.network` で明示的に許可可能）、レビュー・トリアージは `read-only` サンドボックスで動作します。
- **Claude Code**: 実装・修正ロールでは `canUseTool` と `PreToolUse` フックの二重チェックで worktree 外への書き込みや危険なバックグラウンド実行を制限します（入力検査であり OS レベルの隔離ではないため、信頼できないコードにはコンテナ等の別環境を使ってください）。通常レビューとトリアージは `Read` のみ、カスタムコマンド／`local-instructions` レビューは `Read`・`Grep`・`Glob`・`Agent` のみ許可され、フック・埋め込みシェル・MCP は無効です（詳細は [トリアージ・仕様・レビュー・修正](review-and-repair.md)）。
- **仕様ステージ**: `spec-author` と `spec-fix` はリポジトリを読み取り、その run 専用の `spec/spec.md` のみに書き込めます。仕様レビューは読み取り専用です。
- **セッション排他**: 同じ会話セッションへ複数のリクエストを並列送信することはありません。実装・修正でセッションを継続する条件は [リポジトリの設定](configuration.md#修正専用プロファイルprofilesrepairとセッション継続) を参照してください。

## fake モード（模擬実行）

`--provider fake` を使うと、LLM にログインせず・クォータを消費せずにパイプライン全体や復旧の挙動を確認できます。環境変数は CLI ではなく実際にジョブを処理する**ワーカープロセス側**が参照するため、すでに常駐ワーカーが動いている場合は別の `HOME` または `DURABLY_FACTORY_STATE_DIR` で試してください。

| 環境変数               | 設定例と動作                                                     |
| ---------------------- | ---------------------------------------------------------------- |
| `FAKE_FAIL_FIRST`      | `0` を指定すると同梱サンプルの初回 `check` を成功させる          |
| `FAKE_REVIEW_SEQUENCE` | `pass`（即通過）や `needsChanges,pass`（1 回修正後に通過）       |
| `FAKE_LATENCY_MS`      | `20000-90000` のように各呼び出しの待機時間範囲（ms）を指定       |
| `FAKE_USAGE`           | `realistic` で現実的な模擬トークン使用量・コストをレポートに記録 |
