# 計測とレポート

[README](../README.md) に戻る。

## 計測

利用枠が先に尽きるプロバイダーが分かったら、そのプロバイダーの呼び出しがどの工程で増えたかを見ます。モデルや設定を変えるときは、所要時間と消費に加え、納品までに何回の修正が必要だったかを比べます。

```bash
pnpm factory report --run RUN_ID
pnpm factory report --run RUN_ID --format json
pnpm factory report --run RUN_ID --format md --out report.md
```

| 見たいこと                 | レポートの項目                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------- |
| 納品できたか、何回直したか | `summary` の結論、修正回数、レビュー回数                                                                |
| どこで時間がかかったか     | 工程ごとの `work` と `wall`、承認待ちの `inputWait`、その後ワーカーの実行枠を待った `executionSlotWait` |
| どの担当が利用枠を使ったか | `roleUsage` のプロバイダー、モデル、推論量、呼び出し回数、入力・キャッシュ・出力トークン                |
| なぜ手戻りしたか           | `candidates`、検査ログ、レビューの指摘、候補ごとの `reviewCalls`                                        |
| 何を使って動かしたか       | `factoryVersion`、`versions`、`configVersion`                                                           |

`work` は工程内の作業時間の合計、`wall` は工程が始まってから終わるまでの経過時間です。二つのレビューが同時に動くと、作業時間の合計は経過時間より長くなります。run のリードタイムは、登録から終了までです。

トークンはプロバイダーが報告した値です。見えなかった値は `unknown` または JSON の `null` で表します。投入する作業とタイミングは、プロバイダー側に表示される利用枠を見て決めます。

## 複数の実行の比較

同じ題材とベースを使い、モデルやセッションの扱いなど、確かめたい設定を一つ変えて実行します。

```bash
pnpm factory compare --runs RUN_A,RUN_B,RUN_C,RUN_D --format md
pnpm factory compare --trend --days 30
```

- `--runs` は `configVersion` と実行の種類でグループ化します。成功率、結論、修正回数のほか、時間やトークンの中央値・最小・最大と欠測数を確認できます。並列レビューのオン・オフは `configVersion` に含まれないので、対象の run を分けて比べます。
- `--trend` は元の実行と追加修正を一つのタスクにまとめます。最新の実行が終了した週と、初回の実装に使ったモデル・推論量ごとに、件数と初回・最終の承認件数を数えます。進行中は集計から外れ、fake は `--include-fake` で含められます。タスクの所要時間は各実行の時間の合計です。実行の間に空いた時間は含みません。
- `cost per success` は成功した run の費用の統計です。失敗や中断の消費も含めて判断する場合は、各 run の使用量と結論を一緒に見ます。

## 止めた呼び出しの使用量

キャンセル、タイムアウト、検査失敗によるレビューの中止では、最後に受け取った使用量を部分値として残します。部分値を含む集計は不完全と表示します。送信前に止めた呼び出しは `not-sent` となり、使用量に含みません。完了済みのチェックポイントを読み戻した試行は、元の呼び出しと同じ `invocationId` で一度だけ数えます。

## 呼び出し単位の費用とキャッシュ保持時間

費用は実行時の単価を使った API 換算の参考値です。サブスクリプションの請求や利用枠は、契約先で確認します。価格表を更新しても、過去の呼び出しには保存済みの単価が使われます。

- **Codex** は App Server の使用量を使います。ChatGPT ログインで返るキャッシュ書き込みのゼロは不明として扱うため、対応する追加費用を含まない場合があります。
- **Claude** は再開したセッションのモデル別累計から、前回の累計を引いて今回分を求めます。補助モデルとサブエージェントもモデルごとに集計します。キャッシュ書き込みは報告された 5 分・1 時間の保持時間で計算し、内訳や単価が分からない場合は不明とします。
- **再レビュー** は `reviewCalls` に候補、ラウンド、新規・継続の別、所要時間、使用量を残します。最終確認があればその呼び出しも集計します。

### 価格表の定期確認

価格表は `src/engine/model-prices.json` にあります。メンテナーは `pnpm pricing:check` で差分を確認し、`pnpm pricing:check --write` で更新できます。出典と適用単価を確認して `pnpm validate` を実行します。

GitHub Actions の `Model pricing` も登録済みモデルの単価を毎日確認し、変更があれば更新 PR を作ります。新しいモデルや別名は、適用条件を確認して価格表に追加します。

## モデルの選び方とサブスクでの制約

モデルと推論量のプリセットは `pnpm factory --help` で確認できます。アカウントで使えるモデルや推論量は、作業開始前の [事前確認](configuration.md#設定の事前確認preflight) で確かめます。

## `reuse` と `fresh` の比較

対象、ベース、モデル、推論量をそろえ、`--context reuse` と `--context fresh` で動かします。修正回数、キャッシュ読み込み、作業時間と経過時間を比べます。セッションを続けた効果は、実際に報告されたキャッシュ使用量で判断します。再レビューの継続は別の設定です。 [再レビューの実験結果](research/review-session-experiment.md)

## 使用量の責任範囲

実行データはローカル DB と JSON レポートから参照できます。外部の台帳でまとめる場合は、台帳側からレポートを取り込みます。

```bash
pnpm factory report --run RUN_ID --format json \
  | jq '{runId, configVersion, delivery, roleUsage, summary}'
```
